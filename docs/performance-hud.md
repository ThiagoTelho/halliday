# In-game performance measurements

The HUD uses the same host path for Windows OpenVR, Windows OpenXR and native OpenXR. It has no game-name or graphics-API profile. `CompanionFrame.framesPerSecond`, renderer statistics and compositor redraws are not used as the game's frame counter.

- **GAME FPS** is completed producer frame publications per second, measured from the shared `client.frames` counter on the Mac host clock over approximately one second. A consumer poll that observes twelve new frames counts twelve, not one. This is delivered VR producer throughput, not Metal GPU work time or a count of every internal engine render. Host polling quantizes the edges of the averaging window by up to one poll interval.
- **DISPLAY FPS** is cadence from actual physical drawable presentation timestamps. It includes native images, repeated images, generated images and paused menus. It is never used as a substitute for GAME FPS. The host connects this input only while output goes to the physical headset, so a Mac preview does not become a headset measurement.
- **POSE→DISPLAY** is the median software interval from a host pose-publication tag to the first actual **non-generated** presentation of the correlated native image, over approximately one second. A repeated image contributes no additional latency sample. An earlier generated image does not claim a lower native latency. Reordered callback delivery can correct the image's earliest known actual native presentation. The endpoint is presentation **start**, not scanout centre, photons or externally measured motion-to-photon delay.
- **AVG FRAME MS** is `1000 / GAME FPS`: the average publication interval over the throughput window. It is not instantaneous per-frame or GPU execution time. The optional blue graph line is the separately measured pose-to-display interval. Coalesced producer observations do not invent individual per-frame timestamps.

Missing, invalid, evicted or unrelated pose tags show an unavailable latency value. Windows QPC/source-image timestamps are not subtracted from Mac presentation times. Only the host's own pose-publication clock is correlated to `presentedTime`. No target-display estimate or generic lookahead is displayed as measured latency.

The graph retains at most 51 samples over ten seconds and updates at most five times per second. Counter observations, display callbacks, correlated source images and pose stamps are all bounded. Producer changes, counter resets, pause, stale source and disabling retire prior source measurements. Paused contexts may continue collecting actual display cadence while game FPS and latency show unavailable values. Disabling returns an empty snapshot and rejects queued callbacks; GameBridge does not collect new images/history while disabled.

Presentation callbacks must capture both the specific metrics object and its `PresentationContext` **before** GPU/presentation submission. Looking up the current game or current context inside the asynchronous callback could attribute an old image to a new producer. The context generation rejects that stale feedback. The immutable callback itself belongs to the admitted scene, including when the compositor repeats it.

`tools/test-game-performance-metrics.sh` runs CPU-only known-clock fixtures for all three producer identities, native60/display120 with generated repeats, coalesced observations, source stalls, exact pose-tag correlation, invalid/missing tags, wrong clocks, reordered/duplicate callbacks, lifecycle changes, paused display-only measurements, history limits and concurrent callback access. These are software accounting checks, not physical end-to-end latency benchmarks.
